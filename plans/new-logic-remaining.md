## 1. Методология

Каждый абзац обоих файлов сверен с состоянием кодовой базы на 2026-06-13. Подтверждено:

- [`shifts.py`](app/blueprints/shifts.py) — **удалён**, shifts-блупринт не регистрируется в [`__init__.py`](app/__init__.py:132-154)
- [`chat.py`](app/blueprints/chat.py) — полностью мигрирован на `application_id`
- [`notification_service.py`](app/services/notification_service.py) — 7 старых типов уведомлений удалены, остались только актуальные
- [`applications.py`](app/blueprints/applications.py) — withdraw, accept/reject/reopen, apply_job (включая `in_progress`), атомарный PATCH
- [`jobs.py`](app/blueprints/jobs.py) — force-complete, restore, cancel, delete, автопереход `in_progress → active`
- В коде Python **0** упоминаний `payment_pending`, `disputed`, `shifts`, `shift_id`

Из обоих файлов исключены: тестовые сценарии для QA, инструкции Playwright, рекомендации использовать `pg_cron` (недоступен на бесплатном Supabase), визуальные спецификации бейджей (уже реализованы).

### 3.1. Восстановление из cancelled — сброс ВСЕХ старых откликов

| **Текущее состояние** | [`restore_job()`](app/blueprints/jobs.py:637-643) переводит только `accepted → rejected`. `pending`-отклики остаются нетронутыми. |

| **Полезность** | Предотвращает баг «вы уже откликались» на восстановленном задании. Обеспечивает чистоту данных — восстановленное задание должно быть «как новое». |
| **Сложность** | Низкая |
| **Что делать** | В [`restore_job()`](app/blueprints/jobs.py:637) добавить перед сбросом accepted: `supabase_request('DELETE', f'applications?job_id=eq.{job_id}&status=eq.pending')` или `PATCH status=cancelled`. |
| **Приоритет** | **P1** |
