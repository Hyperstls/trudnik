# Runbook: backup и restore БД «Трудник»

**Область:** production (Amvera, PostgreSQL CNPG `trudnik-db`) + media (`/data/uploads`).
**Статус:** процедура подготовлена 2026-11-08; прод-restore ещё **не выполнялся** —
первый прогон только в согласованное окно и только на копию/scratch-БД.
**Не хранить в этом файле пароли и строки подключения.**

## 0. Что защищаем

| Объект | Где | Как бэкапим | RPO | RTO |
|---|---|---|---|---|
| PostgreSQL (профили, задания, отклики, чаты, оценки) | Amvera CNPG `trudnik-db` | `pg_dump -Fc` + штатные снапшоты Amvera | цель ≤ 24 ч | цель ≤ 1 ч |
| Media (фото, документы) | volume `/data` (`/data/uploads`) | снапшот volume / `rsync` на внешнее хранилище | цель ≤ 24 ч | цель ≤ 2 ч |
| `.env` / секреты | панель Amvera | экспорт владельцем, вне репозитория | при изменении | ≤ 15 мин |

RPO/RTO — цели, а не гарантия: после первого реального restore фиксируем фактические цифры.

## 1. Снять прод-дамп (безопасно, без простоя)

Выполняется с машины, у которой есть **админский** URL БД (`DATABASE_ADMIN_URL` из env,
не коммитить). Дамп снимается в режиме чтения и прод не останавливает.

```bash
# пример; значения брать из env, не вставлять в историю shell
DUMP="trudnik-$(date +%Y%m%d-%H%M).dump"
pg_dump "$DATABASE_ADMIN_URL" -Fc -f "$DUMP"
pg_restore --list "$DUMP" | head          # sanity: дамп читается
sha256sum "$DUMP" > "$DUMP.sha256"
```

Правила хранения:

- минимум 7 ежедневных + 4 недельных копий, вне сервера приложения;
- доступ к дампу — как к ПДн (152-ФЗ): шифрование at rest, ограниченный круг;
- дампы старше срока хранения удалять (не «на всякий случай»).

Если `pg_dump` версии не совпадает с сервером — использовать `pg_dump` из контейнера
`trudnik-db` (PostgreSQL 15) или client той же major-версии.

## 2. Репетиция restore — только на копию

**Никогда не восстанавливать поверх production-БД «для проверки».**
Создаём отдельную БД (scratch) на том же или отдельном инстансе:

```bash
# SCRATCH_DATABASE_URL — строка подключения к КОПИИ (отдельная БД/инстанс),
# не DATABASE_URL продакшена.
psql "$DATABASE_ADMIN_URL" -d postgres -c 'CREATE DATABASE trudnik_restore_check'
pg_restore --no-owner --no-acl -d "$SCRATCH_DATABASE_URL" "$DUMP"
```

Проверки после restore (ожидаем совпадение с source на момент дампа):

```sql
SELECT count(*) FROM profiles;
SELECT count(*) FROM jobs;
SELECT count(*) FROM applications;
SELECT count(*) FROM messages;
SELECT count(*) FROM schema_migrations;
```

Дополнительно: `SELECT count(*) FROM pg_tables WHERE schemaname='public';`
и выборочно открыть 2–3 карточки задания/профиля на копии (если поднято приложение).

Локальная автоматическая репетиция той же механики:

```bash
.venv/Scripts/python.exe scripts/backup_restore_rehearsal.py
```

Скрипт делает dump dockerized dev-БД, restore в `<db>_restore_check`, сверяет counts
и удаляет scratch. Зелёный прогон = механика дампа/восстановления рабочая.

## 3. Окно прод-восстановления (только по согласованию)

Предусловия: есть свежий pre-restore дамп; согласовано окно; владелец подтвердил;
понимаем, что данные после дампа будут потеряны (RPO).

1. Зафиксировать начало окна и текущий SHA приложения.
2. Снять **pre-restore** дамп (п. 1) и проверить его читаемость.
3. Остановить приложение (Amvera: остановка проекта/сервиса) — чтобы не было записи.
4. Восстановить БД:
   - предпочтительно — штатным restore Amvera/CNPG из снапшота;
   - либо `pg_restore --clean --if-exists --no-owner --no-acl` (осознанно: `--clean`
     удаляет объекты).
5. Проверить: `schema_migrations` = ожидаемое число (ledger `docs/parity/MIGRATION_LEDGER.md`),
   ключевые counts, расширения (`postgis`, `pgcrypto`).
6. Запустить приложение с `MIGRATIONS_ENABLED=false` (схема уже из дампа), затем smoke:
   `/health` 200, `/jobs` 200, вход, `/admin/login/`, одно задание и один отклик.
7. Включить обычный режим, зафиксировать конец окна и фактические RTO/RPO.

## 4. Rollback

- Ошибка после restore → остановить приложение, восстановить **pre-restore** дамп,
  повторить smoke. Поэтому pre-restore дамп обязателен и не удаляется до конца окна.
- Ошибка на шаге проверки схемы → не запускать приложение, разбирать дамп/версию
  `pg_restore`; прод остаётся на pre-restore состоянии.

## 5. Media

- Проверить, что volume `/data` включён в снапшоты/бэкап Amvera.
- Если снапшотов нет: `rsync -a` каталога `/data/uploads` на внешнее хранилище по расписанию.
- Restore media — отдельно от БД; после восстановления БД проверить 2–3 URL фото
  (файл есть и отдаётся).

## 6. Регулярность и след

- Ежедневно: автоматический дамп БД (или снапшот) + контроль, что файл создан.
- Еженедельно: restore-репетиция на scratch (п. 2) и запись результата.
- Ежемесячно: проверка restore media и пересмотр RPO/RTO.
- Каждая репетиция/окно фиксируется в `docs/parity/MIGRATION_LEDGER.md` или отдельном
  журнале эксплуатации: дата, длительность, результат, расхождения.
