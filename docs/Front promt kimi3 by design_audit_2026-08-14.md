## Обязательная сводка аудита

### Критичные проблемы

1. Раздвоенная айдентика:
   - Tailwind primary выглядит как янтарный, примерно #d97706;
   - в CSS есть переменная --brand: #2563eb, синий;
   - синий фактически используется в чате, кнопках чата, reopen, спиннере, skip-link, приглашениях, статусе open;
   - фиолетовый используется в админке и act-btn;
   - пользователь не считывает единый бренд.

2. Дублирующиеся и рассинхронизированные статусы:
   - есть CSS-классы статусов;
   - есть Jinja-макрос status_badge;
   - цвета одинаковых статусов противоречат друг другу;
   - один и тот же статус может выглядеть по-разному на разных страницах.

3. Низкий контраст вторичного текста:
   - text-neutral-400 и text-neutral-300 используются для важной мета-информации;
   - контраст ниже WCAG 2.1 AA;
   - страдают дата, город, подписи пустых состояний, мета в чате, неактивная навигация.

### Дополнительные проблемы

- нижняя мобильная навигация показывается и на десктопе;
- нет полноценной десктопной навигации;
- шапка перегружена иконками без подписей;
- поиск в шапке ищет только по городу, хотя плейсхолдер обещает больше;
- в регистрации не работает подсветка иконки выбранной роли из-за отсутствия класса group;
- нативный <progress> не стилизован;
- требования к паролю в регистрации и логине рассинхронизированы;
- нет автосохранения черновика задания;
- шаги формы создания задания не интегрированы с history;
- действия вроде отклика требуют полной перезагрузки страницы;
- disabled-кнопки объясняют причину только через title, который не виден на мобильных;
- фильтры работают клиентским скрытием и могут ломаться с пагинацией;
- в чате нет статусов сообщений, разделителей дат, retry при ошибке, textarea с автовысотой;
- эмодзи используются как иконки;
- заголовок карточки задания показывает организацию, а не суть работы;
- пустые состояния не везде имеют CTA;
- нет видимого слоя доверия: рейтинга работодателя на карточке, числа откликов, объяснения оплаты, кнопки «Пожаловаться»;
- есть проблемы доступности: contrast, focus, native confirm(), aria-label у рейтингов, forced-colors, touch targets.

# ДИЗАЙН-СИСТЕМА, КОТОРУЮ НУЖНО ЗАФИКСИРОВАТЬ

Нужно привести интерфейс к единой дизайн-системе «Трудник v1».

## Бренд
Основной бренд-цвет: янтарный.
Рекомендуемый primary: #d97706 или ближайший токен primary-500/600 из текущего Tailwind.

Синий цвет:
- больше не является вторым брендом;
- используется только как info-семантика;
- допустим для информационных статусов, подсказок, ссылок-исключений, но не для основных CTA.

Фиолетовый:
- только для админки или служебных режимов, если это оправдано;
- не должен проникать в пользовательские CTA.

## Семантика цветов
Зафиксируй токены:
- primary = янтарный, основные действия и бренд;
- info = синий, информационные сообщения и статус open;
- success = зелёный, успешные состояния, accepted/active;
- danger = красный, ошибки, rejected/cancelled;
- warning = янтарный/оранжевый, предупреждения, таймеры, in_progress;
- neutral = серый, вторичные и нейтральные состояния.

## Статусы
Нужно создать единый источник правды для статусов.

Базовая таблица:
- open = info / синий;
- pending = neutral или warning, но не должен конфликтовать с open;
- accepted / active = success / зелёный;
- in_progress = warning / primary amber;
- rejected / cancelled = danger / красный;
- withdrawn / completed = neutral.

Если в коде встречаются другие статусы:
1. Собери полный список.
2. Предложи для каждого цвет, иконку и текст.
3. Зафиксируй таблицу в макросе status_badge.

Требования к статус-бейджу:
- один макрос;
- одна цветовая система;
- одна иконка или точка;
- один стиль пилюли;
- понятный текстовый label;
- поддержка aria-live, если статус меняется динамически.

## Иконки
- использовать SVG-иконки из существующего набора, например _icons.html;
- не использовать эмодзи как функциональные иконки;
- эмодзи допустимы только как декоративный контент и с aria-hidden, если они не несут смысл;
- все иконки без текста должны иметь доступную текстовую альтернативу.

## Типографика
- основной контент не должен быть мельче 14px, если это не служебный caption;
- мета-текст карточек минимум 12–13px;
- вторичный текст должен быть читаемым, минимум neutral-500 или выше на светлом фоне;
- заголовки должны иметь ясную иерархию.

## Кнопки
Опиши и используй варианты:
- primary;
- secondary;
- ghost;
- danger;
- icon-button;
- disabled с видимой причиной.

## Пустые состояния
Везде использовать единый макрос empty_state.
У пустого состояния должны быть:
- иконка;
- заголовок;
- пояснение;
- CTA, если есть следующее действие.

## Фаза 1. Quick Wins

Реализуй или детально опиши следующие задачи.

### A1. Единый источник правды для статус-бейджей
Задача:
убрать два противоречащих набора стилей статусов.

Требования:
- оставить один макрос status_badge;
- удалить дублирующиеся CSS-классы или синхронизировать их с макросом;
- все страницы должны использовать один макрос;
- цвет статуса должен задаваться через семантические токены;
- у статуса должна быть точка или иконка;
- текст статуса должен быть понятным на русском.

Результат:
- один статус = один цвет = одна иконка = одна формулировка;
- нет расхождений между страницами.

### A2. Поднять контраст вторичного текста
Задача:
привести ключевой текст к WCAG 2.1 AA.

Требования:
- заменить text-neutral-400 на text-neutral-500 для смыслового текста;
- заменить text-neutral-300 на text-neutral-400 или выше, если текст несёт смысл;
- text-neutral-300 оставлять только для декоративных элементов;
- мета-строки карточек увеличить минимум до 12–13px;
- неактивные пункты нижней навигации сделать не ниже text-neutral-500;
- проверить даты, город, пустые состояния, мета в чате.

Критерий приёмки:
- ключевой текст имеет контраст минимум 4.5:1;
- интерфейс лучше читается на солнце и на ходу.

### A3. Починить подсветку выбранной роли при регистрации
Задача:
выбранная карточка роли должна визуально подсвечивать иконку.

Требования:
- добавить класс group на label.role-card или аналогичный родительский элемент;
- убедиться, что group-has-[:checked]:text-primary-500 работает;
- при выборе роли должна меняться не только рамка, но и иконка;
- проверить keyboard accessibility выбора роли.

Критерий приёмки:
- выбранная роль визуально очевидна;
- иконка выбранной роли окрашивается.

### A4. Карточка задания: суть работы в заголовке
Задача:
главный заголовок карточки должен показывать суть работы, а не только название организации.

Требования:
- заголовок карточки = название задания / вид работы;
- организация показывается вторичной строкой;
- рядом с организацией показать рейтинг, если он есть;
- показать число откликов;
- показать заполненность мест, если данные есть;
- сохранить цену справа;
- сохранить локацию и дату.

Желаемая структура карточки:
Заголовок: «Грузчик на склад (2 дня)»
Вторично: «ООО Ромашка ✓ ★4.8 · 12 отзывов»
Мета: локация, город, дата/время
Цена: справа, заметный бейдж
Низ карточки: CTA, избранное, места/прогресс

Критерий приёмки:
пользователь за 1 секунду понимает:
- что нужно сделать;
- сколько платят;
- где и когда;
- кто работодатель;
- сколько мест осталось.

### A5. Empty states с действием
Задача:
все пустые состояния должны вести пользователя к следующему шагу.

Требования:
- использовать макрос empty_state везде;
- пустая лента работодателя → CTA «Создать задание»;
- пустая лента работника → CTA «Смотреть задания» или «Изменить фильтры»;
- пустой фильтр «Откликнулся» → CTA «Смотреть все задания»;
- после отклонения отклика показать блок «Похожие задания»;
- не оставлять пользователя в голом отказе без следующего действия.

Критерий приёмки:
из любого пустого или негативного состояния есть видимый следующий шаг.

### A6. Убрать мёртвые скелетоны и синий спиннер
Задача:
убрать визуальные артефакты и привести loading к бренду.

Требования:
- удалить фейковые skeleton-loader'ы, которые рендерятся и сразу прячутся;
- либо заменить их на реальную async-загрузку;
- спиннер overlay перекрасить в primary/amber;
- вынести overlay-стили в CSS-классы;
- не использовать синий спиннер вне инфо-контекста.

Критерий приёмки:
- нет мелькания мёртвых скелетонов;
- loading-состояния выглядят как часть дизайн-системы.

### A7. Кнопка «Пожаловаться» и шеринг на детальной задания
Задача:
добавить trust & safety и органический рост.

Требования:
- добавить кнопку или меню «Поделиться»;
- использовать Web Share API, если доступен, иначе копирование ссылки;
- добавить пункт «Пожаловаться»;
- если endpoint уже есть — использовать;
- если endpoint неизвестен — не выдумывать, а предложить контракт;
- кнопка не должна визуально конкурировать с основным CTA.

Критерий приёмки:
пользователь может безопасно пожаловаться и поделиться заданием.

### A8. Причина недоступности действия видна явно
Задача:
disabled-кнопки должны объяснять причину не только через title.

Требования:
- если кнопка «Отозвать отклик» недоступна, показать текст под кнопкой или tooltip с видимым объяснением;
- причина должна быть понятной на мобильных устройствах;
- не использовать title как единственный источник объяснения.

Пример текста:
«Отзыв недоступен: до начала задания осталось менее 12 часов.»

Критерий приёмки:
пользователь без саппорта понимает, почему действие недоступно.

### B3. Поиск по смыслу

### B4. Отклики без перезагрузки страницы
