# Нагрузочный smoke: 100 запросов, P=8

**Цель:** проверить, что прод отвечает под небольшой конкурентностью, и зафиксировать
latency-перцентили. Это **smoke, не стресс-тест**: 100 GET-запросов при 8 параллельных
воркерах. Запуск — только в согласованное окно.

## Скрипт

`scripts/load_test.py` — только GET, без форм/куки/токенов, stdlib (без новых зависимостей).

Локальная проверка самой утилиты (без сети, без прода):

```bash
.venv/Scripts/python.exe scripts/load_test.py --self-test
```

Ожидаемо: `ok: 100 non2xx: 0 errors: 0` и `SELF-TEST OK`, exit 0.

Прод-запуск (в окне, после подтверждения владельца):

```bash
.venv/Scripts/python.exe scripts/load_test.py \
  --base-url https://xn--d1aigknli.xn--p1ai \
  --requests 100 --concurrency 8 --confirm-prod
```

Защита от случайного запуска:

- только `https` и host из allowlist (`xn--d1aigknli.xn--p1ai`, `трудник.рф`);
- обязателен `--confirm-prod`;
- жёсткий cap — 500 запросов, конкурентность 1..32;
- по умолчанию читаются `/jobs`, `/jobs?page=2`, `/health` (все публичные GET, 200).

## Пороги приёмки

| Метрика | Порог |
|---|---|
| 2xx | 100% (0 non-2xx, 0 сетевых ошибок) |
| p95 | ≤ 1000 мс |
| p99 | ≤ 2000 мс |
| max | ≤ 5000 мс |

При провале любого порога — стоп, разбор (Amvera metrics, `error_events`, логи контейнера),
повтор только после устранения.

## Что смотреть в окне

1. До старта: `/health` 200, нет активного деплоя/миграций.
2. Во время: CPU/RAM/сеть проекта в панели Amvera; отсутствие 5xx; отсутствие роста
   `error_events` и `audit_log`-аномалий.
3. После: `/health` и `/jobs` 200; p50/p95/p99 из отчёта; записать результат в журнал
   эксплуатации (дата, окно, цифры).

## Стоп-условие

Любой non-2xx, таймауты, p95 > 1000 мс или деградация `/health` → немедленно прекратить
(скрипт завершится сам после 100 запросов; повтор не запускать) и разбирать причину.

## Ограничения

- Не проверяет авторизованные сценарии (вход, отклик, чат) — только публичные страницы.
- Редиректы не выполняются: 3xx считается non-2xx (цель ограничена allowlist).
- Не заменяет профилирование БД и тест на реальном трафике.
- 100 запросов не показывают предел платформы; задача — убедиться в отсутствии грубых
  проблем и зафиксировать базовые цифры для сравнения после изменений.

## Фактический прогон 2026-11-09 (прод)

Окно согласовано владельцем, 100 GET, P=8, публичные пути `/jobs`, `/jobs?page=2`, `/health`.

| Метрика | Факт | Порог | Итог |
|---|---|---|---|
| 2xx | 100/100 | 100% | ✅ |
| non-2xx / сетевые | 0 / 0 | 0 | ✅ |
| p50 | 709 мс | — | — |
| p90 | 1219 мс | — | — |
| p95 | 1255 мс | ≤ 1000 мс | ⚠️ превышен |
| p99 | 1390 мс | ≤ 2000 мс | ✅ |
| max | 1538 мс | ≤ 5000 мс | ✅ |
| rps | 9.8 | — | — |

Наблюдения:
- `/health` в отдельном зонде: p50 610 мс, p95 1041 мс — заметная часть задержки
  приходится на сеть/хостинг, а не на приложение.
- `/jobs` тяжелее (`p50` ~1005 мс), `/jobs?page=2` — ~1247 мс; ошибок и 5xx нет.
- Первый прогон включал `/` (302 → `/jobs`) и давал non-2xx; второй — тоже с `/`;
  после исключения редиректящих путей — 100/100 2xx. `/workers` публичен (200), но
  в дефолтный набор не входит.

Вывод: под 100 запросами и P=8 прод **отвечает без ошибок**, но ориентир p95 ≤ 1000 мс
не выдержан (1255 мс). Нужно решение: повторить замер из другой сети/после прогрева
и либо принять фактические цифры как baseline для этого тарифа Amvera, либо
оптимизировать `/jobs` (запросы каталога) и повторить. До решения порог p95 считается
**целевым ориентиром, а не пройденным гейтом**.
