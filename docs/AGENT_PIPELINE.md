# AGENT_PIPELINE — управляемый агентный конвейер

Один CLI-скрипт и набор текстовых файлов. Без оркестрационных фреймворков, сети и БД.
Инструмент: [`scripts/tools/pipeline.py`](../scripts/tools/pipeline.py) (Python 3.10+, только stdlib).
Данные: [`context/agent-pipeline/`](../context/agent-pipeline/).

## 1. Зачем

Быстрые/лёгкие модели хорошо решают узкие локальные задачи, но деградируют, когда контекст
раздут, задача не разбита на проверяемые части, нет проверяемого результата и нет отдельного
этапа ревью. Конвейер механически реализует пять принципов:

1. **Изоляция контекста.** Исполнитель получает только файлы контракта и промпт-пак.
2. **Декомпозиция.** ≤4 файла и нумерованные критерии приёмки на задачу.
3. **Внешняя память.** План, статусы, решения — в файлах, чат — только транспорт.
4. **Верификация по exit-коду.** «Выглядит правильно» не принимается.
5. **Независимое ревью.** Ревьюер видит только цель, критерии, out_of_scope и diff.

## 2. Три столпа дисциплины (не упрощать)

**Столп 1. Exit-код — единственный вердикт проверки.**
Проверка пройдена тогда и только тогда, когда команда вернула 0. Текст вывода не анализируется.
`verify` всегда перезапускает проверки сам и пишет лог с фактическими кодами.

**Столп 2. Ревьюер не видит рассуждений исполнителя.**
`review-packet` собирается только из контракта (цель, критерии, out_of_scope) и diff файлов
контракта. Отчёт исполнителя в пакет не попадает — механически, потому что конвейер его не хранит.

**Столп 3. Лимит попыток — и стоп.**
Механические FAIL на `verify`: максимум 3 (`attempts`) → `blocked`.
Содержательные FAIL ревьюера: максимум 2 (`review_rounds`, отдельный счётчик) → `blocked`.
`blocked` — нормальная работа конвейера: дальше решает человек, а не третья догадка модели.

Обходы оставляют след: `verify --skip-scope` требует `--reason` и пишет событие в `state.json`,
строку в `progress.md` и запись в `decisions.md` (кто, когда, почему, какой дрейф обойдён).

## 3. Структура

```
context/agent-pipeline/
  state.json                  # машинное состояние (единственный источник правды)
  progress.md                 # хронология: add/dispatch/verify/review/set
  decisions.md                # решения, измерения, заметки (append-only)
  tasks/<ID>.json             # контракты (канонический JSON)
  packs/<ID>.impl.prompt.md   # промпт исполнителя (генерируется dispatch)
  packs/<ID>.review.prompt.md # промпт ревьюера (генерируется review-packet)
  logs/<ID>.verify.log        # последний лог проверок
  logs/<ID>.baseline/         # снимок файлов контракта на момент dispatch
  selftest/                   # контракты и фикстуры самотеста
  templates/                  # резерв под batch-шаблоны (не обязателен)
```

`baseline` — список изменённых файлов репозитория на момент `dispatch` плюс SHA-256 каждого.
`logs/<ID>.baseline/` хранит снимки файлов контракта, поэтому diff для ревью — это ровно
изменения задачи, без чужих правок, которые уже были в рабочем дереве.

## 4. Быстрый старт

```bash
python scripts/tools/pipeline.py init
python scripts/tools/pipeline.py add --file context/agent-pipeline/selftest/contracts/T1.json
python scripts/tools/pipeline.py dispatch T1
# передать packs/T1.impl.prompt.md исполнителю ДОСЛОВНО
python scripts/tools/pipeline.py verify T1
python scripts/tools/pipeline.py review-packet T1
# передать packs/T1.review.prompt.md ревьюеру ДОСЛОВНО
python scripts/tools/pipeline.py review T1 --ok
```

## 5. Контракт задачи (`tasks/<ID>.json`)

Все поля обязательны. `files` — **ровно** те файлы, которые разрешено менять (1–4).
`context_files` — что можно читать, но нельзя менять. `interfaces` — точные сигнатуры/форматы;
«догадайся» запрещено. `acceptance` — нумерованные проверяемые утверждения. `checks` — команды,
вердикт каждой = exit-код.

```json
{
  "id": "T1",
  "title": "Демо: модуль calc с add и тестами",
  "goal": "В demo/ есть demo/calc.py с add(a, b) и demo/test_calc.py с тестами; проверки зелёные.",
  "why": "Полный цикл конвейера на изолированном модуле.",
  "files": ["demo/calc.py", "demo/test_calc.py"],
  "context_files": [],
  "interfaces": "def add(a, b) -> int | float: возвращает a + b. Без print и зависимостей.",
  "acceptance": [
    "demo/calc.py содержит add(a, b), возвращающую сумму.",
    "demo/test_calc.py содержит минимум 3 теста add.",
    "pytest demo -q завершается с exit-кодом 0."
  ],
  "out_of_scope": ["Не менять файлы вне demo/calc.py и demo/test_calc.py.", "Без сети."],
  "checks": [
    {"name": "compile", "cmd": "{python} -m py_compile demo/calc.py demo/test_calc.py", "cwd": "."},
    {"name": "tests", "cmd": "{python} -m pytest demo -q -p no:cacheprovider", "cwd": "."},
    {"name": "behavior", "cmd": "{python} -c \"import sys; sys.path.insert(0,'demo'); from calc import add; assert add(2,3)==5; print('ok')\"", "cwd": "."}
  ]
}
```

Валидация отклоняет контракт, если: нет обязательного поля; `files` пуст или больше 4;
`checks` пуст; `id` с пробелами/слэшами; путь абсолютный или с `..`; команда многострочная;
`files` и `context_files` пересекаются.

## 6. Проверки: правила

- Одна проверка = одна команда; вердикт = exit-код (0 = PASS). Ничего не парсится «на глаз».
- Офлайн, детерминированно, без интерактива. Фикстуры — во временном каталоге внутри дерева,
  команда сама их создаёт и убирает.
- Минимальный набор: компиляция изменённого, линтер изменённого, юнит-тесты затронутого,
  плюс 1–3 поведенческие проверки, которые падают, если критерий `acceptance` не выполнен.
- `{python}` — плейсхолдер: конвейер заменяет его на текущий интерпретатор. Используйте его,
  чтобы контракт был кроссплатформенным.
- Windows: flake8 с multiprocessing — `--jobs=1`; pytest — `-p no:cacheprovider`.
  Не используйте `>` в PowerShell (UTF-16LE) и `&&`: пусть команда сама пишет файл, python-side.
- `python -c "…"` с кавычками и `<<` ломается об оболочки. Длинные проверки — файлом в
  `context/agent-pipeline/logs/`, а не однострочником.
- Проверки выполняются с `cwd` из контракта (относительно корня репозитория) в окружении
  `PYTHONIOENCODING=utf-8`, `PYTHONUTF8=1`, `PYTHONDONTWRITEBYTECODE=1`.

## 7. Поток ролей

1. **Человек** формулирует задачу.
2. **Оркестратор** пишет контракт, делает `add` → `dispatch`, отдаёт исполнителю
   `packs/<ID>.impl.prompt.md` дословно. Оркестратор не читает код задачи.
3. **Исполнитель** (отдельный вызов без истории чата) меняет только `files`, сам прогоняет
   проверки и возвращает: изменённые файлы, команды, exit-коды, фактический вывод.
4. **Оркестратор** сам запускает `verify` (отчёту исполнителя не доверяет).
5. PASS → `review-packet`; пакет отдаётся **ревьюеру** (отдельный вызов без контекста исполнителя).
   Вердикт: `VERDICT: PASS|FAIL` + блокеры `файл:строка`.
6. FAIL ревьюера → раунд исправлений (максимум 2) → `verify` → `review-packet` снова.
7. `review --ok` → `done`. Память: `progress.md`, `decisions.md`.

## 8. Статусы и переходы

```
planned → implementing → verifying → reviewing → done
                ↑             │           │
                └── fixing ←──┴───────────┘
                        │
                        └── blocked (лимит попыток/раундов)
```

- `dispatch`: `planned → implementing`, снимает baseline и генерирует impl-пак.
- `verify`: `implementing/fixing/reviewing → verifying`; PASS → `reviewing`; FAIL → `fixing`
  (или `blocked` при `attempts >= max_attempts`).
- `review --ok` → `done`; `review --fail` → `fixing` (или `blocked` при
  `review_rounds >= max_review_rounds`).
- `verify` в `blocked` отказывается работать (exit 2) до ручного `set`.
- Повторный `verify` после `done` — диагностический recheck: пишет `logs/<ID>.verify.log`
  и запись `rechecks` в state, но **не меняет** статус, `attempts` и `verify.last`.

Ручной перевод: `set <ID> --status fixing --reason "..." [--reset-attempts] [--reset-review-rounds]`.
Сброс счётчиков — только осознанно, с причиной; переход фиксируется в progress/decisions.

## 9. Scope и spill

Scope = изменения, появившиеся после baseline, минус файлы контракта и spill-исключения.
Spill-паттерны по умолчанию: `/packs/`, `/logs/`, `/tasks/`, `state.json$`, `progress.md$`,
`decisions.md$`, `__pycache__/`, `*.pyc`, `.pytest_cache/`, `.mypy_cache/`, `.ruff_cache/`.
Расширение: `config --spill-add '<regex>'`.

`verify --skip-scope` существует для аварийного случая (чужие процессы в общем дереве),
но требует `--reason`, пишет событие в `state.json`, строку в `progress.md` и запись в
`decisions.md`. Дальше обычный `verify` снова проверяет scope.

## 10. Review-пакет: что внутри и чего нет

Внутри: цель, нумерованные критерии, out_of_scope, полный diff файлов контракта
(baseline → current), список новых файлов, формат вердикта, стратегия чтения большого пакета.

Нет: отчёта/рассуждений исполнителя, истории чата, содержимого файлов вне контракта.
Поэтому ревьюер не может «заразиться» объяснением автора.

## 11. Типовые ловушки

1. Контракт ссылается на канон проекта, а не на самодельные регэкспы.
2. Кэш: ключ включает всё, от чего зависит результат; кэш-хит проходит ту же валидацию.
3. Счётчики не врут молча: дели метрику сразу по каналам/типам.
4. Фолбэк «нет данных — подставь само значение» — дыра в инварианте.
5. Контракт может быть неправ, а код — прав: сначала проверь выполнимость требования.
6. Ревьюер — отдельный вызов с лимитом контекста и стратегией чтения.
7. Чужие процессы портят scope: baseline + spill + `--skip-scope` только со следом.
8. Windows/оболочки: `>` в PowerShell = UTF-16LE, `&&` может не поддерживаться, `$d:` ломает парсер.
9. JSON-контракты пишите инструментом записи целиком, а не точечными правками.
10. «Проверено» должно быть доказуемым: ссылка на источник или причина отказа.
11. Лимит раундов: 2 узких фикса, дальше `blocked` и вопрос человеку.

## 12. Дополнительные команды

- `update <ID> --file <contract> --reason "..."` — замена контракта в `planned/fixing/blocked`.
  Нужна по ловушке №5: если проверка противоречит неизменяемому компоненту, правится контракт.
  Ревизия и причина фиксируются в state/progress/decisions.
- `config` — показать/изменить `max_attempts`, `max_review_rounds`, таймаут проверок,
  spill-паттерны.
- `show <ID>` — контракт + состояние задачи (без `baseline_hashes`).
- `status --json` — машинное состояние целиком; `list` — таблица и итоги.
- `note <ID> "текст"` — заметка/измерение в `decisions.md` вне scope-контроля.

## 13. Самотест

Контракты самотеста: `context/agent-pipeline/selftest/contracts/T1..T7.json`;
невалидные фикстуры: `selftest/invalid/`. Прогон покрывает: happy path с субагентами,
отказ невалидных контрактов, scope-дрейф, падающую проверку и рост `attempts`, лимит попыток,
лимит раундов ревью, дисциплину exit-кода, след `--skip-scope`, повторный `verify` после `done`.
Фактические команды и exit-коды приведены в отчёте о выполнении задания.

## 14. Пересечения с существующим кодом

В проекте не было скриптов оркестрации задач или каталога контрактов. Конвейер живёт в
собственных `context/agent-pipeline/` и `scripts/tools/pipeline.py`, не меняет существующий код.
Демо-модуль `demo/` создан только для самотеста.
