# 152-ФЗ: ПДн и потоки данных (auth / registration / profile)

Документ фиксирует **технические** факты и риски. Правовую базу (согласия, сроки,
уведомление РКН, договоры с операторами) подтверждает владелец; это не юридическое заключение.

## 1. Какие ПДн собираются

| Категория | Где | Риск |
|---|---|---|
| Email, ФИО, город, телефон | регистрация/профиль | обычные ПДн |
| Контакт (`contact`), портфолио | профиль | обычные ПДн; **Django отдаёт `contact` публично (P0-03)** |
| ИНН, самозанятость | Flask-регистрация/профиль; Django-профиль | юридически значимые ПДн; **Django не валидирует ИНН (P1-02)** |
| Документ верификации (паспорт/скан) | `/profile/verification-doc` | чувствительные ПДн; **Django: доступ любому авторизованному (P0-02)** |
| Вероисповедание (`religion_id`) | Django-профиль | **спецкатегория, 152-ФЗ ст.10 (P0-04)** |
| Возраст, bio, опыт, желаемая оплата | профиль | обычные ПДн |
| Аватар/фото | uploads | изображение; legacy `photo_url` |
| Сообщения, отклики, оценки, жалобы | БД | обычные ПДн |
| Push-подписки, настройки уведомлений | БД | идентификаторы устройства |

## 2. Потоки

| Поток | Куда | Статус |
|---|---|---|
| Регистрация | PostgreSQL (Amvera, РФ) | ок; consent обязателен, `consented_at` пишется |
| Подтверждение email / сброс пароля | SMTP-провайдер | **провайдер не зафиксирован в коде**; нужен договор/локализация РФ |
| Капча | `https://smartcaptcha.yandexcloud.net/validate` (Яндекс, РФ) | ок по локализации; **Django не передаёт IP (P2-09)** |
| MAX-верификация | MAX Bot API (РФ) | ок; проверить согласие на передачу |
| Аватары/фото заданий | `/uploads/...` (диск Amvera) | публично; ок |
| Документы верификации | `/uploads/verification-docs/...` | **должны быть owner/admin; Django — любой авторизованный (P0-02)** |
| Экспорт ПДн | JSON-файл пользователю | ок; Django исключает `password` (улучшение) |
| Удаление аккаунта | `delete_user_cascade` | **файлы на диске не удаляются (P1-14)** |
| Логи | stdout/файлы | `_send_mail` логирует email при ошибке (`views_auth.py:70`); проверить retention/маскирование |

## 3. Находки, критичные для 152-ФЗ

1. **P0-02. Документы верификации.** Django `serve_upload` проверяет только
   `is_authenticated`; Flask — owner/admin. Плюс `Cache-Control: public, max-age=86400`
   на том же ответе (`views_profile_ext.py:211`) — риск кэширования приватного документа
   в прокси/браузере. Требуется: owner/admin, `Cache-Control: private, no-store`,
   `Content-Disposition: attachment`, аудит-лог доступа.
2. **P0-03. Публичный `contact`.** `PUBLIC_PROFILE_FIELDS` включает `contact` и
   `religion_id`; шаблон `worker_detail.html:46-47` рендерит `contact`. Flask эти поля
   не выбирает. Требуется: убрать `contact`/`religion_id` из публичного набора;
   `email_public` оставить только при явном согласии пользователя.
3. **P0-04. Вероисповедание.** Django `ProfileForm` снова собирает `religion`;
   Flask удалил как спецкатегорию. Требуется: убрать поле из формы и API; хранить
   только если есть отдельное законное основание и согласие (сейчас его нет).
4. **P1-14. Удаление файлов.** `delete_user_cascade` удаляет строки, но не файлы
   `uploads/avatars`, `uploads/verification-docs`, `uploads/jobs`. После удаления
   аккаунта ПДн остаются на диске. Требуется: удаление файлов по URL из профиля/заданий
   (или фоновой purge) + запись в audit log.
5. **P1-10. `email_verified=true` default.** Любой путь создания профиля в обход RPC
   даёт подтверждённого пользователя. Требуется: default `false` в БД/модели или
   явная установка в каждом пути.
6. **P1-12. RLS обходится.** `trudnik`/`trudnik_dj` — BYPASSRLS. Компенсация —
   queryset-фильтры; нужна контрактная матрица IDOR (см. CONTRACT_CHECKS п.22).
7. **P2. Логи.** Не логировать email/телефон/ИНН в открытом виде; проверить
   `_redact_sensitive`-аналог в Django (в Flask он есть).
8. **P2. Consent при регистрации.** Django ставит `consented_at` отдельным UPDATE после
   RPC; если UPDATE не выполнится, пользователь создан без отметки согласия. Нужна
   транзакция/проверка результата.

## 4. Что проверить у владельца/DevOps

- Регион/юрисдикция PostgreSQL и Redis (Amvera MSK — РФ?).
- SMTP-провайдер: РФ или трансграничная передача; договор поручения.
- MAX Bot API: договор/согласие на передачу ПДн.
- Сроки хранения: профиль, сообщения, verification-docs, логи, бэкапы.
- Политика конфиденциальности/согласие: соответствие фактическому набору полей
  (сейчас Django собирает меньше полей при регистрации, но больше в профиле — тексты
  могут разойтись).
- Процедура удаления: БД + файлы + бэкапы; срок реакции на запрос субъекта.
- Роли БД: можно ли перейти на `trudnikapp` (NOBYPASSRLS) для read-only/публичных
  запросов и оставить `trudnik_dj` только для админских операций.

## 5. Вывод

До исправления P0-02/03/04 Django **нельзя** считать соответствующим 152-ФЗ в части
доступа к ПДн и минимизации спецкатегорий, даже если бизнес-логика остального паритета
выглядит полной. Эти три пункта — блокеры перед любым релизом/заявлением о паритете.
