## КОНТЕКСТ ПРОЕКТА И СТЕК (сверено с кодом)

**Backend web:** Flask 3.1.3 (WSGI, Application Factory + 21 Blueprints, включая faq и messenger_verify). Точка входа — `asgi.py` (`RouterMiddleware`): `websocket`+`lifespan` → FastAPI; `http` → Flask через `a2wsgi.WSGIMiddleware(flask_app, workers=15)`. В проде `uvicorn asgi:application --workers 2` (один процесс, HTTP и WS вместе).
**Backend WS:** FastAPI 0.137.1 (ASGI). Единственный WS-эндпоинт — `@app.websocket("/ws")` в `websocket_server/main.py`. WS **push-only**: инбаунд-сообщения не диспетчиризуются (нет JSON-RPC), есть только проверка первого сообщения `{type:'auth', token}` в течение 10с (`asyncio.wait_for`, timeout→close `1008 POLICY_VIOLATION`), origin-check (close code `4003` при mismatch, но при `CORS_ORIGINS=["*"]` dev-режим пропускает все), max 3 соединения/пользователь (`active_connections: dict[str,set]`), flood-guard (>120 сообщений/10с → дисконнект). Пуши приходят из Redis Pub/Sub каналов `notifications` и `chat` (`redis_pubsub_listener`). Heartbeat: клиент шлёт `ping`, сервер отвечает `pong`. WS-сервер имеет свой `GET /health` (Redis ping + active_connections count).
**База данных:** прод — PostgreSQL 17.6 + PostGIS (Amvera CloudNativePG, msk0/Москва); локально — PostgreSQL 15 + PostGIS 3.4 (docker-compose, `postgis/postgis:15-3.4-alpine`, init-скрипт `migrations/067_bootstrap_amvera.sql`).
**API-слой:** PostgREST **v14** (прод=локаль, parity). PostgREST отдаёт свой OpenAPI в корне `/` (контракт доступен). JWT-клеймы отдаются только как `request.jwt.claims` (JSON), RLS-политики читают `current_setting('request.jwt.claims', true)::json->>'app_role'` / `->>'user_id'` (миграции 124/125; прецедент — `tests/test_rls_integration.py` фиксит баг: при v12→v14 сломались все 39 RLS-политик, молча возвращая NULL). Мутации — PL/pgSQL `SECURITY DEFINER` (~22 RPC), конвенция `SET search_path` конфликтует с pgcrypto/PostGIS (`gen_salt`/`crypt`/`ST_MakePoint`) — миграции 127/130/131 чинили падения.
**Async:** Celery 5.6.3 + Redis 8 (прод) / 7-alpine (лок, пароль `trudnik-local-dev`). Broker=db0, result-backend=db1. `task_acks_late=True`, `prefetch_multiplier=1`, `task_time_limit=300`, `soft=240`, `max_retries=3`, `task_default_retry_delay=60`, `task_reject_on_worker_lost=True`. 7 beat-задач (карта ниже). `FlaskContextTask` инъектит `_request_id` из Flask `g` во все задачи из request-context.
**Сессии:** Redis-backed server-side (`SESSION_TYPE='redis'`, `SESSION_USE_SIGNER=True`, `SESSION_KEY_PREFIX='session:'`). В куке только подписанный `session_id`. `PERMANENT_SESSION_LIFETIME=3600` (1 час). Ротация session-id при логине (защита от fixation). В `TESTING` (`conftest.py:app_client`) сессии принудительно переключаются на `SecureCookieSessionInterface` (cookie-roundtrip без живого Redis).
**Auth/JWT:** bcrypt 12 rounds. **Два секрета**: `PGRST_JWT_SECRET` (PostgREST, HS256) и `WEBSOCKET_JWT_SECRET` (WS; payload только `user_id`+`jti`, без `app_role`; mint через `GET /api/ws/token`). `ACCESS_TOKEN_TTL_SECONDS=3600` (1 час, синхронно с сессией). Per-request токен для PostgREST (`get_user_headers`). `app_role` (worker/employer/admin) берётся из **сессии**, не из ввода клиента → кейс на попытку подмены `app_role` в JWT. jti-чёрный список: Redis-ключ `jti_blacklist:{jti}` (отзыв при logout/смене пароля). `login_required` (`app/decorators.py`): decode JWT (`verify_exp=False`, ручная проверка exp + silent refresh) → jti-blacklist → `password_changed_at` (B10, cache 60с) → существование пользователя (B5, cache 60с) → флаг `suspended` (Phase3, cache 30с), **fail-open при недоступности БД**. `admin_required` — DB re-check через `postgrest_admin_request`, **fail-closed** (X8).
**service_role / BYPASSRLS:** `postgrest_admin_request` — mint `role='service_role'`, обходит RLS. Защита: `_ADMIN_ALLOWED_PREFIXES` (allowlist вызывающих модулей) + `_ADMIN_WARN_PREFIXES` (**warn-но-NOT-block** — только логирует warning, не прерывает; реальная защита — RLS) + блокировка вызова из Jinja2 render context (`caller` thread-local можно спуфить — кейс). `/admin/reset-circuit-breaker` гейтится `X-Admin-Token` (CSRF-exempt, **fail-closed 503** если токен не задан — X12).
**CSRF:** session-based (`session['_csrf_token']`), `app/middleware.py:csrf_check` на все POST/PUT/PATCH/DELETE. Приоритет источников: заголовок `X-CSRF-Token` → form `csrf_token`/`_csrf_token` → JSON body `csrf_token`/`_csrf_token`, сравнение через `hmac.compare_digest`. Отключён в `TESTING`. Exempt: GET/HEAD/OPTIONS, `/admin/reset-circuit-breaker` (X-Admin-Token), `/messenger/webhook/*` (одноразовый Redis-токен, TTL 10 мин). `SESSION_COOKIE_SAMESITE='Strict'`. CSRF-кука `csrf_token` (httponly=False, samesite=Lax) выдаётся для Service Worker в `add_security_headers`.
**Идемпотентность (мидлware):** `app/middleware.py:check_idempotency` — на POST/PUT/PATCH/DELETE проверяет заголовок `X-Client-Request-Id` (валидный UUID), для авторизованных пользователей. Cache-key `idempotency:{user_id}:{client_request_id}`, TTL 24ч, кэширует только успешные (2xx) JSON-ответы; при повторе — возвращает кэшированный ответ с заголовком `X-Idempotency-Replayed: true`. Отдельно — `client_message_id` в чате (`POST /api/send_message`) для дедупликации сообщений (миграция 121). В API-клиенте (`static/js/api.js`) `apiFetch` авто-генерирует `X-Client-Request-Id` UUID для мутаций.
**Rate limiting (3 уровня):** (1) глобальный per-IP `before_request` (`app/__init__.py`), `GLOBAL_RATE_LIMIT_PER_MIN=120`, Redis-ключ `iprl:{ip}`, INCR+EXPIRE 60, **fail-open**, отключён в `TESTING`, exempt `/static/`,`/health`,`/ready`,`/favicon.ico`; (2) декоратор `@rate_limit` (`app/utils/rate_limit_decorator.py`, Lua-скрипт, `fail_open` параметр; auth-эндпоинты — `fail_open=False` fail-closed); (3) `/api/client-error` — 20/мин/IP; (4) body cap `MAX_CONTENT_LENGTH=16MB`; (5) WS flood-guard 120/10с.
**Circuit Breaker:** 2 экземпляра (`_cb_postgrest`, `_cb_admin`), `CB_FAILURE_THRESHOLD=10`, `CB_RECOVERY_TIMEOUT=60`, 403 НЕ триггерит. `/health` отражает состояние CB → `status:'degraded'`. Сброс через `POST /admin/reset-circuit-breaker` (X-Admin-Token).
