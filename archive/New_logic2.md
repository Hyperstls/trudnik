# 🎭 ДОПОЛНЕНИЕ К ПРОМТУ #5: UI/UX State Machine & Feedback Loop Testing

**ИНСТРУКЦИЯ ДЛЯ АГЕНТА:** Бизнес-логика может быть идеальной, но если пользователь не видит нужную кнопку в нужный момент или не получает подтверждения своего действия — продукт сломан. Твоя задача — проверить **динамический UI (State-Based Rendering)** и **петлю обратной связи (Feedback Loop)** для каждого статуса задания и роли.

---

## 📋 10.1. Матрица видимости UI-элементов (State-Based UI Rendering)

Агент должен для каждого статуса задания проверять **наличие (visible)** или **отсутствие (hidden/detached)** конкретных кнопок и бейджей в DOM. Используй `page.locator().isVisible()` и `expect(locator).toBeHidden()`.

### 🟢 Статус: `open` (Оплачено, приём откликов)

| Роль | Обязаны быть в DOM (Visible) | Обязаны отсутствовать (Hidden/Detached) |
|------|------------------------------|-----------------------------------------|
| **Работодатель** | Бейдж `Оплачено`, Кнопка `Редактировать` (если current=0), Кнопка `Отозвать задание`, Кнопки `Принять`/`Отклонить` (на карточках откликов), Счётчик откликов | Кнопка `Оплатить`, Кнопка `Восстановить`, Кнопка `Завершить` |
| **Трудник (нет отклика)** | Кнопка `Откликнуться` | Кнопка `Начать смену`, Кнопка `Отозвать`, Кнопка `Написать в чат` |
| **Трудник (pending)** | Кнопка `Отозвать отклик`, Бейдж `Отклик отправлен` | Кнопка `Откликнуться`, Кнопка `Написать в чат` |
| **Трудник (rejected)** | Кнопка `Откликнуться снова`, Бейдж `Отклик отклонён` | Кнопка `Отозвать`, Кнопка `Написать в чат` |
| **Гость** | Кнопка `Войти, чтобы откликнуться` | Кнопка `Откликнуться` |

### 🟡 Статус: `in_progress` (Набраны все места, смена не началась)

| Роль | Обязаны быть в DOM | Обязаны отсутствовать |
|------|--------------------|-----------------------|
| **Работодатель** | Бейдж `Все места заняты`, Счётчик `3/3 принято`, Кнопка `Отозвать работника` (только если до смены >12ч), Кнопка `Написать в чат` (для accepted) | Кнопка `Редактировать задание`, Кнопка `Отозвать всё задание`, Кнопка `Принять` (если нет свободных мест) |
| **Трудник (accepted)** | Кнопка `Написать в чат`, Кнопка `Отозвать отклик` (если >12ч до смены), Бейдж `Принято` | Кнопка `Откликнуться`, Кнопка `Начать смену` |
| **Трудник (нет отклика)** | Бейдж `Мест нет` (если current=max) ИЛИ Кнопка `Откликнуться` (если есть свободные места после отзыва) | Кнопка `Начать смену` |

### 🔵 Статус: `active` (Наступило время начала)

| Роль | Обязаны быть в DOM | Обязаны отсутствовать |
|------|--------------------|-----------------------|
| **Работодатель** | 🔴 Кнопка `Завершить задание` (красная, warning), Кнопка `Написать в чат`, Бейдж `Задание началось` | **ВСЕ** кнопки управления (Отозвать, Редактировать, Принять) |
| **Трудник (accepted)** | Кнопка `Написать в чат`, Бейдж `Задание началось` | Кнопка `Отозвать отклик`, Кнопка `Начать смену` |
| **Трудник (pending/rejected)** | Бейдж `Задание началось, приём закрыт` | Кнопка `Откликнуться` |

### 🟣 Статус: `completed` (Завершено работодателем)

| Роль | Обязаны быть в DOM | Обязаны отсутствовать |
|------|--------------------|-----------------------|
| **Работодатель** | Бейдж `Завершено`, Кнопка `Оценить работника` (для каждого accepted), Кнопка `В избранное`, Кнопка `Удалить (Архив)` | Все активные кнопки управления |
| **Трудник (accepted)** | Бейдж `Задание завершено`, Кнопка `Оценить работодателя` | Все активные кнопки |
| **Трудник (rejected)** | Бейдж `Задание завершено`, Бейдж `Отклик отклонён` | Кнопка `Оценить` |

### 🔴 Статус: `cancelled` (Отозвано работодателем)

| Роль | Обязаны быть в DOM | Обязаны отсутствовать |
|------|--------------------|-----------------------|
| **Работодатель** | Кнопка `Восстановить задание`, Кнопка `Удалить навсегда`, Бейдж `Отменено` | **ВСЕ** активные кнопки управления откликами |
| **Трудник (любой статус)** | Бейдж `Задание отменено` | Кнопка `Откликнуться`, Кнопка `Написать в чат` |

## 🔔 10.2. Тестирование Toast-уведомлений (Feedback Loop)

В `base.html` реализована функция `window.showToast(message, type)`. Агент должен перехватывать эти вызовы или проверять появление DOM-элемента тоста.

**Как тестировать в Playwright:**
```javascript
// Перехват вызова toast через evaluate
await page.addInitScript(() => {
    window.__toasts = [];
    const originalShowToast = window.showToast;
    window.showToast = (message, type) => {
        window.__toasts.push({ message, type, timestamp: Date.now() });
        if (originalShowToast) originalShowToast(message, type);
    };
});

// В самом тесте:
const toasts = await page.evaluate(() => window.__toasts);
expect(toasts.some(t => t.message.includes('Смена начата'))).toBeTruthy();
```

### Матрица ожидаемых Toast-уведомлений

| Действие пользователя | Ожидаемый Toast (type) | Проверка |
|-----------------------|------------------------|----------|
| **Отклик отправлен** | `success`: "Отклик отправлен работодателю" | Появляется мгновенно |
| **Отклик отозван (pending)** | `info/success`: "Отклик отозван" | Кнопка меняется на "Откликнуться" |
| **Отклик отозван (accepted, >12ч)** | `success`: "Отклик отозван, место освобождено" | Статус задания может измениться |
| **Попытка отзыва (accepted, <12ч)** | `error`: "Отозвать можно не позднее чем за 12 часов до начала" | Кнопка остаётся активной |
| **Работодатель принял отклик** | `success`: "Кандидат принят" | Счётчик увеличивается |
| **Работодатель отклонил отклик** | `info`: "Кандидат отклонен" | Кнопка меняется на "Отклонено" |
| **Массовое принятие (3 чел.)** | `success`: "Принято 3 кандидата" | Все 3 карточки обновляются |
| **Массовое отклонение (5 чел.)** | `success`: "Отклонено 5 кандидатов" | Все 5 карточек обновляются |
| **Автоматический переход open→in_progress** | `info`: "Все места заняты! Задание в ожидании начала" | Бейдж появляется |
| **Автоматический переход in_progress→open** | `info`: "Задание снова открыто для откликов" | Кнопка "Откликнуться" появляется |
| **Автоматический переход in_progress→active** | `info` (при обновлении): "Задание началось" | Бейдж "Задание началось" |
| **Принудительное завершение** | `success`: "Задание завершено, непринятые отклики отклонены" | Все pending→rejected |
| **Оценка сохранена** | `success`: "Спасибо за оценку!" | Кнопка "Оценить" исчезает |
| **Попытка оценить до completed** | `error`: "Оценка доступна после завершения задания" | Оценка не сохраняется |
| **Двойной клик по кнопке** | `warning`: "Действие уже выполняется" | Кнопка disabled |
| **Восстановление из cancelled** | `success`: "Задание восстановлено, старые отклики сброшены" | Счётчики обнулены |
| **Ошибка геолокации (старая логика)** | `error`: "Вы находитесь слишком далеко" | Н/Д (удалено) |

## ⚠️ 10.3. Тестирование модальных окон и Предупреждений (Guards)

Некоторые действия требуют подтверждения или блокируются с объяснением причины.

### Сценарий 1: Отзыв принятого отклика < 12 часов до смены
1. Трудник открывает задание в статусе `in_progress` (до смены 5 часов).
2. Нажимает кнопку `Отозвать отклик`.
3. **Ожидаемое поведение:** 
   - Появляется **Toast (error)**: *"Отозвать принятый отклик можно не позднее чем за 12 часов до начала смены"*
   - Кнопка `Отозвать` **не срабатывает**
   - Статус отклика и задания **не меняются**

### Сценарий 2: Принудительное завершение задания
1. Работодатель нажимает `Завершить задание` в статусе `active`.
2. **Ожидаемое поведение:** 
   - Появляется **модальное окно** или **нативный confirm**: *"Завершить задание? Все непринятые отклики будут отклонены"*
   - При отмене — ничего не происходит
   - При подтверждении — массовый `POST` запрос и Toast `success`

### Сценарий 3: Попытка редактирования при наличии принятых откликов
1. Работодатель пытается перейти по прямому URL `/job/<id>/edit` для задания в статусе `in_progress`.
2. **Ожидаемое поведение:** 
   - Бэкенд делает редирект на `/jobs/<id>` с Toast `error`: *"Редактирование недоступно: есть принятые работники"*
   - Кнопка "Редактировать" в UI должна быть скрыта через Jinja2 `{% if job.current_workers == 0 %}`

### Сценарий 4: Массовое отклонение (Подтверждение)
1. Работодатель выделяет 5 откликов и жмёт "Отклонить выбранные".
2. **Ожидаемое поведение:** 
   - Нативный `confirm("Вы уверены, что хотите отклонить 5 кандидатов?")` или кастомная модалка
   - При отмене — ничего не происходит
   - При подтверждении — массовый `POST` запрос и Toast `success`

### Сценарий 5: Восстановление из cancelled
1. Работодатель нажимает "Восстановить задание".
2. **Ожидаемое поведение:** 
   - Подтверждение: *"Все предыдущие отклики будут сброшены. Продолжить?"*
   - При подтверждении — все старые отклики удаляются, `current_workers=0`

| Контекст | Подсказка (UI Hint) | Проверка |
|----------|---------------------|----------|
| **Задание истекает через 2 дня** | Бейдж `⏳ Осталось 2 дня` рядом с ценой | Проверить рендеринг на карточке работодателя |

| **Задание завершено автоматически** | Бейдж `✅ Все места заняты` + `⏳ Ожидание начала` | Проверить в статусе `in_progress` |
| **Есть непринятые отклики в active** | Счётчик: `2 принято из 5 откликов` | Проверить в статусе `active` |

## 🔄 10.6. Оптимистичные обновления UI (Optimistic UI Updates)

В `favorites.js` и `applications.js` реализованы оптимистичные обновления. Агент должен проверить:

### Сценарий 1: Добавление в избранное (Успех)
1. Трудник нажимает "В избранное" на карточке работодателя.
2. **Ожидаемое поведение:** 
   - Кнопка **мгновенно** меняет иконку/текст (`updateButtonUI()`)
   - Отправляется `POST /api/favorites/add`
   - При успехе — ничего не меняется (UI уже обновлён)
   - Toast `success` не обязателен (визуальное подтверждение достаточно)

### Сценарий 2: Добавление в избранное (Ошибка сети)
1. Трудник нажимает "В избранное".
2. Кнопка мгновенно меняется.
3. Запрос падает с ошибкой (сеть/500).
4. **Ожидаемое поведение:** 
   - Кнопка **откатывается** к исходному состоянию
   - Toast `error`: "Не удалось добавить в избранное"

### Сценарий 3: Принятие отклика (Успех)
1. Работодатель нажимает "Принять" на карточке отклика.
2. **Ожидаемое поведение:** 
   - Кнопка `Принять` **мгновенно** меняется на `✓ Принято` (disabled)
   - Счётчик `current_workers` увеличивается на 1
   - Если `current_workers == max_workers` → бейдж `Все места заняты` появляется
   - Toast `success`: "Кандидат принят"

### Сценарий 4: Принятие отклика (Ошибка)
1. Работодатель нажимает "Принять".
2. Кнопка меняется.
3. Запрос падает (например, RLS violation).
4. **Ожидаемое поведение:** 
   - Кнопка откатывается к `Принять`
   - Счётчик не увеличивается
   - Toast `error`: "Не удалось принять отклик"

## 📱 10.7. Адаптивность UI-элементов

### Мобильная версия (360x800)
| Элемент | Проверка |
|---------|----------|
| Кнопки `Принять`/`Отклонить` | Не должны перекрываться, минимум 44x44px |
| Бейджи статусов | Не должны обрезаться, текст читаем |
| Модальные окна | Не должны выходить за пределы viewport |
| Toast-уведомления | Должны появляться сверху/снизу, не перекрывая кнопки |
| Счётчики (`3/3`) | Должны быть видны без прокрутки |

### Десктопная версия (1920x1080)
| Элемент | Проверка |
|---------|----------|
| Карточки откликов | Должны быть в сетке (grid/flex), не в один столбец |
| Кнопки массовых операций | Должны быть видны без прокрутки |
| Бейджи | Должны быть выровнены правильно |

## 🛠 10.8. Инструкции для Playwright (Обработка диалогов и Toast)

Чтобы агент не "зависал" на нативных диалогах и корректно читал тосты, добавь этот сетап в `beforeEach`:

```javascript
// 1. Автоматическое принятие confirm/prompt (если не тестируем их специально)
page.on('dialog', async dialog => {
    if (dialog.type() === 'confirm') await dialog.accept();
    if (dialog.type() === 'prompt') await dialog.accept('123'); // ID задания для приглашения
});

// 2. Перехват Toast-уведомлений (Mock window.showToast)
await page.addInitScript(() => {
    window.__toasts = [];
    window.__toastErrors = [];
    const originalShowToast = window.showToast;
    window.showToast = (message, type) => {
        window.__toasts.push({ message, type, timestamp: Date.now() });
        if (type === 'error') window.__toastErrors.push(message);
        if (originalShowToast) originalShowToast(message, type);
    };
});

// 3. Проверка отсутствия ошибок в консоли
page.on('console', msg => {
    if (msg.type() === 'error') {
        console.log('Console Error:', msg.text());
    }
});

// В самом тесте:
const toasts = await page.evaluate(() => window.__toasts);
const errors = await page.evaluate(() => window.__toastErrors);
expect(toasts.some(t => t.message.includes('Кандидат принят'))).toBeTruthy();
expect(errors).toHaveLength(0); // Не должно быть ошибок
```

## 📋 10.9. Финальный чек-лист UI/UX для отчёта агента

После прогона E2E-тестов агент должен добавить в отчёт секцию **UI/UX State Coverage**:

### Видимость кнопок
- [ ] **Статус `open`**: Кнопка "Откликнуться" видна труднику, скрыта для работодателя
- [ ] **Статус `in_progress`**: Кнопка "Редактировать" **физически удалена из DOM** (не просто disabled)
- [ ] **Статус `active`**: Кнопка "Завершить задание" видна только работодателю
- [ ] **Статус `completed`**: Кнопка "Оценить" видна только для `accepted` откликов
- [ ] **Статус `cancelled`**: Кнопка "Восстановить" работает только для работодателя

### Toast-уведомления
- [ ] При автоматическом переходе `open→in_progress` появляется Toast `info`
- [ ] При отзыве `accepted` отклика <12ч появляется Toast `error`
- [ ] При принудительном завершении появляется Toast `success`
- [ ] При ошибке сети Toast `error` + откат UI

### Модальные окна
- [ ] Принудительное завершение требует подтверждения
- [ ] Восстановление из `cancelled` требует подтверждения
- [ ] Массовые операции требуют подтверждения

### Бейджи и индикаторы
- [ ] Бейдж `Оплачено` появляется после оплаты
- [ ] Бейдж `Все места заняты` появляется при `current=max`
- [ ] Бейдж `Задание началось` появляется в статусе `active`
- [ ] Счётчик `3/3 принято` отображается корректно

### Адаптивность
- [ ] На мобильных (360x800) кнопки не перекрываются
- [ ] Toast-уведомления не перекрывают интерактивные элементы
- [ ] Модальные окна не выходят за пределы viewport

### Оптимистичные обновления
- [ ] Кнопка "В избранное" меняется мгновенно
- [ ] При ошибке сети UI откатывается
- [ ] Счётчик `current_workers` обновляется без перезагрузки

## 🎯 Приоритет тестирования UI/UX

**Критические проверки (Priority 1):**
1. Кнопка "Отозвать отклик" disabled/скрыта при <12ч до смены
2. Кнопка "Завершить задание" появляется только в статусе `active`
3. Toast при автоматических переходах статусов
4. Оптимистичные обновления с откатом при ошибке

**Важные проверки (Priority 2):**
1. Бейджи статусов с правильными цветами
