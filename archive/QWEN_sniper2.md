# 🚀 ДОПОЛНЕНИЕ К ПРОМТУ #3: Скрытые ловушки, UI-диалоги и Настройки

**ИНСТРУКЦИЯ ДЛЯ АГЕНТА:** В архитектуре зашиты специфические паттерны (нативные браузерные диалоги, JSON-настройки уведомлений, двойная загрузка CSS). Добавь эти сценарии в свой фреймворк, иначе тесты упадут или пропустят критические баги.

## 🪤 8.1. Ловушка нативного `prompt()` (Критично для Playwright)
*   **Контекст:** В разделе 8.3 указано, что приглашение трудника работает через нативный браузерный диалог: `prompt("Введите ID задания")`.
*   **Проблема:** Playwright не видит нативные `alert`/`confirm`/`prompt` как элементы DOM. Если агент просто нажмет кнопку «Пригласить», тест **навсегда зависнет**, ожидая ввода.
*   **Инструкция для агента:** 
    ```javascript
    // Агент ОБЯЗАН использовать обработчик диалогов ДО клика по кнопке
    page.on('dialog', async dialog => {
        expect(dialog.type()).toContain('prompt');
        await dialog.accept('123'); // Вводим ID задания
    });
    await page.click('text=Пригласить');
    ```

## 🎨 8.2. Архитектурный конфликт Tailwind (Performance Test)
*   **Контекст:** В разделе 6.3 указано: *"Tailwind CSS v3 через CDN (Play CDN) — динамическая компиляция в браузере"* И *"Кастомные стили в tailwind.min.css (33 KB) — скомпилированная версия"*.
*   **Проблема:** Использование Play CDN в продакшене (или на тестовом стенде) — это антипаттерн, который убивает производительность PWA и ломает офлайн-режим (CDN не кэшируется Service Worker'ом так, как локальные файлы).
*   **Тест:** 
    1. Открой DevTools -> Network.
    2. Проверь, какой именно CSS загружается. 
    3. *Ожидаемый результат:* Должен грузиться **только** локальный `tailwind.min.css` (33 KB). Если агент видит загрузку `cdn.tailwindcss.com` (весом ~300+ KB) — это **Critical Performance Bug**, который нужно зафиксировать в отчете, так как это ломает `Cache First` стратегию в `sw.js`.

## 🔔 8.3. Глубокая проверка `notification_prefs` (JSON в БД)
*   **Контекст:** В таблице `profiles` есть поле `notification_prefs` (JSON), позволяющее пользователям отключать конкретные из 18 типов уведомлений (Раздел 8.6).

    2. Отправь ему сообщение в чат (`POST /api/send_message`).
    3. *Проверка БД:* В таблице `notifications` **НЕ** должна появиться запись с `type='new_message'` для этого пользователя.
*   **Тест 2 (Фильтрация ленты):** Раздел 8.6 гласит: *"приглашения трудника ("Вас пригласили") исключаются из общего списка уведомлений"*.
    1. Создай приглашение для трудника.
    2. Зайди на `/notifications`.
    3. *Ожидаемый результат:* Приглашения там **НЕТ** (оно должно быть только на отдельной странице `/invitations`).

## 🔄 8.4. Кросс-страничная синхронизация состояний (UI/UX)
*   **Контекст:** Раздел 8.3: *"при загрузке любой страницы (/workers, /favorites) бэкенд проверяет существующие приглашения и отображает «✓ Приглашён»"*.
*   **Тест:**

    2. Перейди на страницу `/favorites` (если трудник там есть).
    3. *Ожидаемый результат:* Кнопка приглашения рядом с этим трудником **уже должна быть** в состоянии `✓ Приглашён` (бэкенд инжектит статус при рендере Jinja2).
    4. Вернись на `/workers` (назад в браузере). Состояние кнопки должно сохраниться.

## 💰 8.5. Динамические тарифы и ИНН (Бизнес-логика)

# 🚀 ДОПОЛНЕНИЕ К ПРОМТУ #4: Technical Debt, Timezones и Production Readiness

**ИНСТРУКЦИЯ ДЛЯ АГЕНТА:** Мы покрыли бизнес-логику и безопасность. Теперь проверь приложение на устойчивость к реальным условиям эксплуатации, сетевым сбоям и скрытому техническому долгу, зашитому в схему БД.

## 🕳 9.1. Обнаружение технического долга (Схема БД vs Код)
*   **Контекст:** В Разделе 8.5 сказано: *"Старая модель (pay-per-contact) полностью удалена... paywall из откликов убран"*. **ОДНАКО** в Разделе 5.1 (Таблицы) в схеме таблицы `applications` до сих пор указаны поля `contact_paid` и `contact_payment_id`.
*   **Тест (Схема и ORM):** 
    1. Сделай `POST /apply/<job_id>` (отклик на задание).
    2. Проверь SQL-запрос (или ответ Supabase). 
    3. *Ожидаемый результат:* Код **НЕ** должен пытаться передать `null` или значения в `contact_paid` / `contact_payment_id`, если эти поля были удалены из миграций, но остались в схеме документа (или наоборот: если поля есть в БД, но код их не заполняет, не нарушает ли это NOT NULL constraint?).
    4. *Проверка:* Убедись, что при создании отклика не возникает ошибок `column "contact_paid" of relation "applications" does not exist` или `null value in column "contact_paid" violates not-null constraint`.

## 🌍 9.2. Часовые пояса и Даты (Критично для смен)
*   **Контекст:** В таблице `jobs` есть `date_time`, а в `shifts` — `checkin_time` и `complete_time`. gig-экономика живет по часам.
*   **Тест 1 (Смещение времени):** 
    1. Работодатель (с локальным временем, например, МСК) создает задание на "Завтра, 10:00".
    2. Трудник (эмулируй другой часовой пояс через `page.emulate_media(timezone_id='Asia/Vladivostok')`) открывает это задание.
    3. *Ожидаемый результат:* Время должно корректно конвертироваться и отображаться с учетом часового пояса трудника (или явно указываться часовой пояс работодателя).
*   **Тест 2 (Длительность смены):**
    1. Трудник делает Check-in, ждет (или мокает время), делает Complete.
    2. *Проверка:* Если логика расчета оплаты или штрафов зависит от разницы `complete_time - checkin_time`, убедись, что расчет идет в UTC, а не в локальном времени браузера, иначе смена "длинной" в 2 часа может посчитаться как 14 часов из-за перехода через полночь.

## 🛡 9.3. Idempotency (Защита от Double-Click)
*   **Контекст:** Фронтенд использует Vanilla JS. Что произойдет, если пользователь будет яростно кликать по кнопке?
*   **Тест 1 (Двойная оплата):**
    1. На странице `/job/<id>/publish` с помощью Playwright перехвати клик и отправь **3 одновременных** `POST /api/jobs/<id>/publish` запроса.
    2. *Проверка БД:* В таблице `job_payments` должна создаться **ровно одна** запись. Либо фронтенд должен блокировать кнопку (disabled) сразу после первого клика, либо бэкенд (`PaymentService`) должен проверять, что для этого `job_id` уже есть `pending` или `paid` платеж.
*   **Тест 2 (Массовый отклик):**
    1. Трудник выделяет 5 заданий и быстро 3 раза кликает "Откликнуться на выбранные".
    2. *Проверка:* Не должно создаться дубликатов откликов (статус `pending` должен быть уникален для пары `job_id` + `worker_id`).

## 🌐 9.4. Deep Linking и TWA Navigation
*   **Контекст:** Приложение распространяется через Google Play как TWA (Trusted Web Activity). Пользователи будут шерить ссылки на задания в мессенджерах.
*   **Тест 1 (Холодный старт по Deep Link):**
    1. Закрой все вкладки. Перейди напрямую по ссылке `https://<your-domain>/jobs/123` (где 123 — существующее open-задание).
    2. *Ожидаемый результат:* Страница должна загрузиться, Service Worker должен корректно инициализироваться, CSRF-токен должен быть доступен в `meta`-теге или `inject_csrf_token` для последующих AJAX-запросов (например, "В избранное").
*   **Тест 2 (404 на Deep Link):**
    1. Перейди по ссылке `/jobs/999999` (несуществующее).
    2. *Ожидаемый результат:* Должен отобразиться кастомный шаблон `error.html` (404), а не стандартная белая страница ошибок Werkzeug/Flask.

## 🌩 9.5. Отказоустойчивость (Supabase Downtime)
*   **Контекст:** Бэкенд использует обертку `SupabaseResponse`. Как приложение ведет себя, когда база данных "лежит"?
*   **Тест (Симуляция 503 Service Unavailable):**
    1. Через `page.route('**/rest/v1/**', route => route.fulfill({ status: 503, body: 'Service Unavailable' }))` заблокируй все запросы к Supabase REST API.
    2. Попробуй зайти на главную `/`, открыть профиль `/profile`, отправить сообщение.
    3. *Ожидаемый результат:* 
        * Flask **НЕ** должен падать с 500 Internal Server Error и выдавать Stack Trace (это уязвимость).
        * Должен срабатывать глобальный обработчик ошибок, показывая пользователю `error.html` (500) с текстом "Сервис временно недоступен".
        * В логах Gunicorn должна быть запись об ошибке, но сессия пользователя не должна "ломаться" (куки не должны биться).

## 🧩 9.6. Регистрация и M2M Связи (`user_skills`)
*   **Контекст:** Раздел 9 (Потоки данных) описывает регистрацию: `Supabase Auth -> PATCH /profiles -> POST /user_skills`.
*   **Тест (E2E Регистрация):**
    1. Зарегистрируй нового трудника через UI (`/register`).
    2. На шаге выбора навыков выбери **0 навыков** (если это возможно) и **максимально возможное количество**.
    3. *Проверка БД:* Записи в `user_skills` должны корректно создаться.
    4. *Негативный тест:* Попробуй через API `POST /user_skills` передать `skill_id`, которого нет в справочнике `skills`. *Ожидаемый результат:* Ошибка FK (Foreign Key Violation), которая корректно обрабатывается бэкендом и возвращается как 400 Bad Request, а не 500.
