### 🔹 1. BACKEND (Приоритет: КРИТИЧЕСКИЙ)

#### 1.1. Бизнес-логика и RPC-функции
Проверь атомарность и корректность следующих операций:
- **`accept_application(p_job_id, p_app_id)`**
  - Блокировка строки (`SELECT FOR UPDATE`)
  - Проверка `current_workers < max_workers`
  - Корректное обновление статуса задания (`open` → `completed` при достижении лимита)
  - Массовый reject остальных pending-заявок
  - Откат при ошибке
- **`reject_application`** — уменьшение `current_workers`, возврат статуса `open` при 0 workers
- **`delete_job_cascade`** — удаление из всех связанных таблиц (applications, job_skills, job_photos, invitations, notifications)
- **`delete_user_cascade`** — полное удаление пользователя из `auth.users` и всех связанных данных

**Сценарии гонок (race conditions):**
- 10 одновременных откликов на последнее свободное место
- 5 одновременных accept/reject одного задания
- Concurrent accept + delete_job_cascade

#### 1.2. API-эндпоинты (REST + RPC)
Протестируй все 80+ маршрутов из blueprint'а по следующей матрице:

| Метод | Auth | Role | Happy Path | Negative Cases |
|-------|------|------|------------|----------------|
| GET/POST | ✅ | worker/employer/admin | 200/201/302 | 400, 401, 403, 404, 409, 429, 503 |

**Особое внимание:**
- `/api/applications/<id>/accept|reject|reopen` — только owner-employer
- `/apply/<job_id>` — проверки: не owner, не в ЧС, есть места, статус open
- `/api/invite/<job_id>/<worker_id>` — нет дубликатов, есть места
- `/cancel-job/<id>` — запрет при наличии accepted-заявок
- `/restore-job/<id>` — только из статуса `cancelled` (409 при других)

#### 1.3. Аутентификация и сессии
- Автообновление JWT через `refresh_token` при истечении `access_token`
- 3 попытки с exponential backoff при 429 от Supabase Auth
- Очистка сессии при неудачном refresh
- Rate limit: 10 запросов / 60 секунд на IP
- Редиректы: worker → `/`, employer → `/my-jobs`

#### 1.4. Валидация данных
- ИНН: ровно 12 цифр (для worker)
- Стоп-слова в jobs: `["ставка", "зарплата", "штат", "трудовая", "график", "постоянная работа", "вахта"]`
- Длины: title≤255, description≤5000, address≤500, bio≤1000, message≤2000
- Файлы: фото (jpg/png/gif/webp, ≤5MB), документы (pdf/jpg/png)
- UUID-валидация для всех FK

### 🔹 4. БЕЗОПАСНОСТЬ (Приоритет: КРИТИЧЕСКИЙ)

#### 4.1. CSRF-защита
- POST без `_csrf_token` → 400
- Неверный токен → 400
- Исключения: GET/HEAD/OPTIONS, `/login`, `/register`

#### 4.2. XSS-защита
- **Чат:** `html.escape(content, quote=True)` — проверь `<script>alert(1)</script>`, `<img src=x onerror=...>`, SVG-injection
- **PostgREST инъекция:** `?city=Москва' OR '1'='1` → санитизация через `sanitize_postgrest()`
- **URL-декодирование** и whitelist-фильтрация

#### 4.3. CSP и Security Headers
Проверь наличие во всех ответах:
```
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-...' https://cdn.jsdelivr.net https://api-maps.yandex.ru
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Strict-Transport-Security
Referrer-Policy
Permissions-Policy
```

#### 4.4. Rate Limiting и Circuit Breaker
- **Rate limit:** 10 запросов / 60 сек с одного IP → 429
- **Circuit Breaker:** 5 последовательных ошибок → OPEN (30 сек) → HALF_OPEN → CLOSED при успехе
- При OPEN: все запросы → 503

#### 4.5. Авторизация и RLS
- Worker не может PATCH/DELETE чужие jobs
- Worker получает 403 при доступе к `/blacklist`
- Guest не может выполнять POST-действия
- Admin видит всё (обход RLS через `service_role`)
- Проверка `employer_id != user_id` при отклике на своё задание

# 🚨 ADDENDUM: Advanced QA & Hidden Risks Coverage

## 🔐 1. Security Deep-Dive (IDOR, PII и RLS Bypass)

Поскольку фронтенд ходит в базу через PostgREST (`supabase_request`), главная угроза — **IDOR (Insecure Direct Object Reference)** и утечка чувствительных данных (PII).

### Тест-кейсы на IDOR и PostgREST:
| # | Сценарий | Ожидаемый результат |
|---|----------|---------------------|
| 1 | **PII Leak в профилях:** Worker запрашивает `/profile/<employer_id>`. | Поля `inn`, `contact` (телефон), `email` должны быть скрыты или маскированы, если `email_public = false`. |

## 🎯 СТРАТЕГИЯ ТЕСТИРОВАНИЯ (6 СЛОЕВ АУДИТА)

### 🧱 СЛОЙ 1: BACKEND & БИЗНЕС-ЛОГИКА (Приоритет: CRITICAL)

#### 1.1. Атомарность и Race Conditions (RPC)
Протестируй функции `accept_application`, `reject_application`, `delete_job_cascade` под нагрузкой:
*   **Сценарий "Последнее место":** Задание с `max_workers=1`. 50 воркеров одновременно отправляют POST `/apply` и `/api/.../accept`. **Ожидаемо:** Только 1 получает `accepted`, 49 — `rejected` (или 409 Conflict). `current_workers` не должен стать > 1.
*   **Сценарий "Фантомный Accept":** Employer делает `accept` в тот же миллисекунд, когда Worker делает `withdraw`.
*   **Сценарий "Reopen Race":** Одновременный `reopen` и `reject` одного и того же отклика.

#### 1.2. Массовые операции (Batch & Array Limits)
*   **`/apply-selected` и `/unapply-selected`:** Что если передать массив из **10,000 `job_ids`**? (Проверка на OOM, таймауты Gunicorn, SQL `IN (...)` лимиты).
*   **`/api/applications/batch`:** Лимит `MAX_BATCH_SIZE=50`. Передача 51 элемента должна вернуть **400 Bad Request**, а не 500 или частичное выполнение.
*   **Partial Success:** Массовый `accept` 10 заявок, но на 5-й заканчиваются места (`max_workers`). Должен ли откатиться весь батч (транзакция) или вернется `{"accepted": 4, "failed": 6}`?

#### 1.3. Редактирование заданий (Бизнес-ловушки)
*   **Правило:** "Редактирование с accepted-откликами: можно менять только description и contact_phone".
*   **Тест:** Задание имеет 1 accepted-отклик. Через DevTools/Postman отправить PATCH, изменив `payment_amount`, `date_time` или `max_workers`. **Ожидаемо:** Жесткий отказ (403 Forbidden).

#### 1.4. Конфликт статусов Чата (UX Bug)
*   **Правило 1:** Чат доступен для `accepted`-заявок.
*   **Правило 2:** Отправка сообщений разрешена только если задание в статусе `completed`.
*   **Правило 3:** Задание становится `completed` только когда `current_workers >= max_workers`.
*   **Тест:** Задание с `max_workers=5`. 1 работник принят (статус задания `open`, статус заявки `accepted`). **Вопрос:** Доступен ли чат? Если нет — это критический UX-баг (работник принят, но не может связаться).

#### 1.5. Каскадное удаление и ILIKE (Data Loss Risk)
*   **RPC `delete_job_cascade`:** Удаляет уведомления по `ILIKE '%job_id%'`.
*   **Тест:** Создать задание с ID `abc-123`. Создать уведомление для ДРУГОГО задания с текстом "Обновлено задание abc-12345". Удалить `abc-123`. **Ожидаемо:** Уведомление для `abc-12345` **НЕ должно** удалиться. (ILIKE здесь — архитектурный дефект, требующий фикса на точное совпадение JSONB `data->>'job_id'`).

### 🛡️ СЛОЙ 2: БЕЗОПАСНОСТЬ (Приоритет: CRITICAL)

#### 2.1. IDOR и PostgREST Injection
Поскольку Flask проксирует запросы к Supabase:
*   **PII Leak:** Worker запрашивает `/profile/<employer_id>`. Поля `inn`, `contact` (телефон), `email` должны быть скрыты, если `email_public = false`.
*   **PostgREST Injection:** В параметр поиска `?city=Москва` передать `?city=Москва&select=*,applications(*)`. Функция `sanitize_postgrest()` должна вырезать операторы `select`, `join`, `!inner`.
*   **RLS Bypass:** Worker A логинится. В DevTools меняет запрос `GET /rest/v1/applications?worker_id=eq.<ID_A>` на `worker_id=eq.<ID_B>`. **Ожидаемо:** RLS Supabase возвращает `[]` или `401`. Если вернутся данные — **Critical Data Breach**.

#### 2.2. CSRF и Production-конфигурация
*   В коде: "CSRF отключена в `TESTING` режиме".
*   **Тест:** Убедиться, что в Production (`TESTING=False` или `FLASK_ENV=production`) CSRF **включена**. POST-запрос без `X-CSRF-Token` должен вернуть 400.
*   **Обход:** Попробовать отправить форму с `Content-Type: text/plain` (иногда bypass-ит JSON-парсеры).

#### 2.3. XSS и Чат
*   **Тест:** Отправить в чат: `<script>alert(1)</script>`, `<img src=x onerror=alert(1)>`, `<svg/onload=alert(1)>`, `javascript:alert(1)`.
*   **Ожидаемо:** `html.escape(content, quote=True)` должен превратить это в безопасный текст. Проверить рендеринг в DOM.

#### 2.4. Обход Стоп-слов (ТК РФ ст. 15)
Закон запрещает указывать слова, подразумевающие трудовые отношения (`"ставка"`, `"зарплата"`, `"вахта"`).
*   **Тест на обфускацию:** Ввод `"з/п"`, `"з.п."`, `"зар.плата"`, `"вахта 15/15"`, `"трудоустройство"`, `"ЗАРПЛАТА"`, `"3арплата"` (латиница/цифры).
*   **Ожидаемо:** Валидатор должен использовать регулярные выражения и словари синонимов, а не просто `in string`.

### ⚙️ СЛОЙ 3: ИНФРАСТРУКТУРА И ДЕПЛОЙ (Приоритет: HIGH)

#### 3.1. Multi-Worker Gunicorn (Render.com)
*   **Rate Limit Bypass:** In-memory rate limit (10 req / 60 sec). Запусти 2 воркера Gunicorn. Сделай 10 запросов (упри лимит). 11-й запрос路由 на другой воркер — он **пройдет**. Это архитектурный баг. Задокументируй необходимость Redis для Rate Limit.
*   **Circuit Breaker Reset:** In-memory Circuit Breaker сбрасывается при рестарте воркера. Проверь поведение при `kill -HUP` воркера Gunicorn.

#### 3.2. Таймауты Gunicorn vs Долгие RPC
*   **Сценарий:** `delete_user_cascade` для пользователя с 500 заданиями, 10,000 откликов и 50,000 сообщений.
*   **Тест:** Выполнение может занять > 30 секунд (дефолтный таймаут Gunicorn). Воркер умрет, транзакция откатится, пользователь увидит 502 Bad Gateway. **Решение:** Проверить, используются ли фоновые задачи (Celery/RQ) или таймаут увеличен.

#### 3.3. Supabase Storage (Ghost Files & Bloat)
*   **Тест:** Worker загружает аватар (v1). Обновляет профиль, загружает новый (v2). **Ожидаемо:** Файл v1 должен быть физически удален из бакета Storage через `supabase.storage.from('avatars').remove()`. Иначе проект разорится на хостинге.
*   **Приватность:** Документы верификации (`verification_doc_url`) должны лежать в **приватном** бакете. Прямая ссылка без `service_role` токена должна отдавать 403.

#### 3.4. Миграции (`apply_migrations.py`)
*   **Идемпотентность:** Запустить скрипт дважды. Второй проход не должен падать.
*   **Транзакции:** PostgREST (`exec_sql`) может не поддерживать явные `BEGIN/COMMIT`. Проверь, что миграции атомарны.

### 🎨 СЛОЙ 4: FRONTEND, UX/UI И PWA (Приоритет: HIGH)

#### 4.1. Memory Leaks в JavaScript
*   **Чат Polling:** В `chat.html` используется `setInterval` для `GET /api/messages/.../poll`. **Тест:** Открыть чат, перейти на другую страницу, вернуться. Убедиться, что старые интервалы очищены (`clearInterval`), иначе браузер "съест" память и положит вкладку.
*   **Offline Queue:** `localStorage` имеет лимит ~5MB. **Тест:** Забить очередь 10,000 фейковых офлайн-действий. Проверить, не упадет ли JS с `QuotaExceededError`.

#### 4.2. N+1 Проблема в Jinja2 (Производительность)
*   В `base.html` есть контекстные процессоры: `unread_notifications`, `pending_invitations`, `pending_app_count`.
*   **Тест:** Загрузить любую страницу с включенным логом SQL-запросов. **Ожидаемо:** Не должно быть 3 дополнительных `SELECT COUNT(*)` на каждый рендер. Счетчики должны браться из кэша (Redis/Session) или обновляться асинхронно.

#### 4.3. Адаптивность и "Notch" (Safe Areas)
*   **Тест:** Открыть приложение на iPhone 14/15 Pro (эмулятор). Проверить, что Bottom Navigation не перекрывается системной полосой (Home Indicator). Должен использоваться `padding-bottom: max(env(safe-area-inset-bottom), 16px)`.
*   **Фильтр навыков:** На мобильных это Bottom Sheet. Проверить, что его можно закрыть свайпом вниз (или кликом на backdrop), а не только крестиком.

#### 4.4. SEO и Sitemap.xml
*   **Тест:** Скачать `/sitemap.xml`. **Ожидаемо:** В нем должны быть ТОЛЬКО публичные страницы (`/jobs/<id>`, `/profile/<id>`). Там **НЕ должны** попасть `/my-jobs`, `/admin`, `/chats`, `/notifications`.
*   **Open Graph:** Проверить `<meta property="og:image">` на странице задания. Картинка должна быть абсолютным URL (с `https://`), иначе Telegram/WhatsApp не подтянут превью.

### 🔥 СЛОЙ 5: 10 ХАРДКОРНЫХ E2E СЦЕНАРИЕВ

Пройди эти сценарии от начала до конца, фиксируя каждый чих:

1.  **"Призрак в Хранилище" (Storage Bloat):** Загрузить 10 фото в профиль -> Удалить аккаунт (`delete_user_cascade`). Проверить через Supabase Admin API, что бакет Storage пуст.
2.  **"Timezone Exploit":** Employer (МСК) создает задание на "10:00 завтра". Worker (Калининград, +1 час) пытается отозвать accepted-заявку за 13 часов до начала (по его локальному времени). Сервер должен сравнивать время в **UTC**.
3.  **"IDOR через URL":** Worker перехватывает запрос `GET /rest/v1/applications?worker_id=eq.<ID_A>` и меняет ID. RLS должен заблокировать.
4.  **"Массовый Отказ (Partial Success)":** Employer делает `batch accept` на 10 заявок, но `max_workers=5`. Первые 5 принимаются, остальные 5 отклоняются. UI должен корректно обновиться без перезагрузки страницы.
5.  **"Обход Стоп-слов Unicode":** Создание задания со словом `зӑрплӑта` (кириллица с диакритикой) или `zarp1ata`.
6.  **"Гео-Спуфинг":** Employer через DevTools подставляет `lat/lng` Красной Площади, но выбирает город "Владивосток". Сервер должен валидировать соответствие координат городу (или логировать аномалию).
7.  **"Фантомное Приглашение":** Employer приглашает Worker, но Worker уже откликнулся и был отклонен (`rejected`). Что происходит с `current_workers`?
8.  **"Чеки и Монетизация":** Проверить таблицы `receipts` и `tariff_settings`. Если код пытается сгенерировать чек, но падает из-за отсутствия полей — зафиксировать Dead Code.
9.  **"Search Vector Lag":** Employer редактирует `title` задания. Сразу после этого Worker ищет новое название. **Ожидаемо:** Триггер PostgreSQL должен обновить `search_vector` мгновенно. Если поиск не находит — баг триггера.
10. **"PWA TWA Asset Links":** Запросить `/.well-known/assetlinks.json`. JSON должен быть валидным, содержать правильный SHA256-отпечаток сертификата и package name Android-приложения (для Trusted Web Activity).

### ⚠️ СЛОЙ 6: EDGE CASES (Граничные условия)

| # | Сценарий | Ожидаемый результат |
|---|----------|---------------------|
| 1 | `max_workers=0` или отрицательное | Ошибка валидации (CHECK constraint или Flask) |
| 2 | `max_workers=10000` | Работает, но массовый accept может упасть по таймауту |
| 3 | Невалидный UUID `/jobs/not-a-uuid` | 404 или 400 (не 500 Internal Server Error) |
| 4 | Удалённое задание `/jobs/<deleted_id>` | Flash «Задание не найдено», редирект |
| 5 | Истёкший токен без `refresh_token` | Очистка сессии, редирект на `/login` |

| 7 | Загрузка файла > 5MB (или .exe) | Ошибка валидации (Whitelist: jpg/png/gif/webp/pdf) |

| 11 | Восстановление не-cancelled задания | 409 Conflict |
| 12 | Редактирование не-своего задания | 403 Forbidden |
| 13 | Самооценка (rating на себя) | Отказ (400/403) |
| 14 | Оценка не-completed задания | Отказ |
| 15 | XSS в чате: `<script>alert(1)</script>` | Экранирование (`&lt;script&gt;`) |

| 17 | 51 элемент в batch (MAX=50) | 400 Bad Request |

| 20 | Удаление уведомлений через `delete-all` | **Критично:** Приглашения (`type='invitation'`) НЕ удаляются |

| 25 | Поиск по `search_vector` с опечатками | FTS PostgreSQL должен поддерживать префиксный поиск (`plainto_tsquery`) |
| 26 | Регистрация с `skill_ids`, которых нет в БД | Ошибка валидации UUID (FK constraint) |
