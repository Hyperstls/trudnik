## 1. Цель (goal)

Письма подтверждения email и сброса пароля ставятся в Celery-очередь; при недоступности брокера — синхронный fallback, регистрация/сброс не ломаются.

## 2. Зачем (why)

Django send_mail синхронный: SMTP блокирует request-цикл (AUTH-P1-05). Нужен async + fallback, без изменения outbox/prefs.

## 4. Интерфейсы (не выдумывать и не «улучшать»)

settings.TRANSACTIONAL_EMAIL_ASYNC = env 'TRANSACTIONAL_EMAIL_ASYNC' (default true; '0'/'false' -> false). tasks.send_transactional_email(bind=True, max_retries=3, default_retry_delay=60, ignore_result=True)(subject, message, to_email): send_mail(subject, message, None, [to_email]); при исключении logger.warning + self.retry(exc). views_auth._send_mail: если TRANSACTIONAL_EMAIL_ASYNC — try send_transactional_email.delay(...), return; при ошибке enqueue — logger.warning и синхронный send_mail fallback; иначе синхронный send_mail. tests/test_auth_flows.py: LOCMEM добавить TRANSACTIONAL_EMAIL_ASYNC=False (существующие mail-тесты остаются синхронными); новые тесты RegisterTests.test_transactional_email_enqueued (override True, patch core.tasks.send_transactional_email.delay, assert called once, mail.outbox пуст) и test_transactional_email_fallback_on_broker_error (override True, patch delay side_effect=RuntimeError, mail.outbox 1).

## 5. Критерии приёмки

1. При TRANSACTIONAL_EMAIL_ASYNC=True письмо ставится в очередь через send_transactional_email.delay.
2. При ошибке enqueue выполняется синхронный fallback, письмо уходит, регистрация не падает.
3. При TRANSACTIONAL_EMAIL_ASYNC=False поведение синхронное, существующие mail-тесты зелёные.
4. Celery-задача ретраит SMTP-ошибку (max_retries=3).
5. core.tests.test_auth_flows и core.tests.test_tasks проходят.

## 9. Типовые ловушки (реальные ошибки, стоившие раундов):
1. Контракт ссылается на канон проекта, а не на самодельные регэкспы.
2. Кэш: ключ включает ВСЁ, от чего зависит результат; ветка кэш-хита проходит ту же валидацию.
3. Счётчики не врут молча: метрику, которая должна делиться по каналам/типам, дели сразу.
4. Фолбэк «нет данных — подставь само значение» — дыра в инварианте. Формулируй, что НЕЛЬЗЯ.
5. Контракт может быть неправ, а код — прав. Сначала проверь выполнимость требования.
6. Ревьюер — отдельный вызов с лимитом контекста: заголовок и критерии → grep → range-чтения.
7. Другие процессы портят scope. Отсюда baseline и spill-исключения; `--skip-scope` — только со следом.
8. Windows/оболочки: `>` в PowerShell = UTF-16LE; `&&` может не поддерживаться; `$d:` ломает парсер.
9. JSON-контракты пиши инструментом записи целиком, а не точечными правками со вставками `\n`.
10. «Проверено» должно быть доказуемым: у факта — ссылка на источник, у отсечённого — причина.
11. Лимит раундов: 2 узких фикса на задачу. Дальше `blocked` и вопрос человеку.
