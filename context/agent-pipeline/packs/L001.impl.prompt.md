## 1. Цель (goal)

Страницы /privacy, /terms, /safety доступны без записей site_pages: view рендерит fallback-шаблон из legacy-контента; SitePage остаётся override.

## 2. Зачем (why)

E2E smoke: site_pages пуст -> privacy/terms/safety 404; ссылка согласия 152-ФЗ при регистрации ведёт на /privacy (P0).

## 4. Интерфейсы (не выдумывать и не «улучшать»)

legal_page(request, slug): page=SitePage.objects.filter(pk=slug).first(); если page -> как сейчас core/legal_page.html; иначе для slug in {'privacy','terms','safety'} -> render core/legal_fallback.html с {'slug','title'}; иначе Http404. LEGAL_TITLES: privacy='Политика конфиденциальности', terms='Условия использования', safety='Как мы защищаем'. legal_fallback.html: extends core/base.html, title block с {{ title }}, content block с {% if slug == 'privacy' %}...{% elif slug == 'terms' %}...{% elif slug == 'safety' %}...{% endif %}; контент скопировать из legacy templates/privacy.html, terms.html, safety.html (внутри block content, без extends/block-обёрток; заменить Jinja url_for на прямые пути, если есть). Тест test_public_views.LegalFallbackTests: удалить SitePage privacy/terms/safety, GET reverse('core:privacy'/'terms'/'safety') -> 200 и ключевой текст; создать SitePage(slug='privacy', content='<p>DB-OVERRIDE</p>') -> GET /privacy содержит DB-OVERRIDE.

## 5. Критерии приёмки

1. GET /privacy, /terms, /safety при пустом site_pages -> 200, не 404.
2. Fallback-контент соответствует legacy-страницам (заголовок и ключевые разделы).
3. При наличии SitePage используется его content (override).
4. Неизвестный slug -> 404.
5. core.tests.test_public_views проходит.

- Не менять SitePage-модель/админку и другие страницы.

## 9. Типовые ловушки (реальные ошибки, стоившие раундов):
1. Контракт ссылается на канон проекта, а не на самодельные регэкспы.
2. Кэш: ключ включает ВСЁ, от чего зависит результат; ветка кэш-хита проходит ту же валидацию.
3. Счётчики не врут молча: метрику, которая должна делиться по каналам/типам, дели сразу.
4. Фолбэк «нет данных — подставь само значение» — дыра в инварианте. Формулируй, что НЕЛЬЗЯ.
5. Контракт может быть неправ, а код — прав. Сначала проверь выполнимость требования.
6. Ревьюер — отдельный вызов с лимитом контекста: заголовок и критерии → grep → range-чтения.
7. Другие процессы портят scope. Отсюда baseline и spill-исключения; `--skip-scope` — только со следом.
8. Windows/оболочки: `>` в PowerShell = UTF-16LE; `&&` может не поддерживаться; `$d:` ломает парсер.
9. JSON-контракты пиши инструментом записи целиком, а не точечными правками со вставками `\n`.
10. «Проверено» должно быть доказуемым: у факта — ссылка на источник, у отсечённого — причина.
11. Лимит раундов: 2 узких фикса на задачу. Дальше `blocked` и вопрос человеку.
