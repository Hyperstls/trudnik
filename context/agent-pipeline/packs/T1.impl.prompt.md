## 1. Цель (goal)

В demo/ существуют demo/calc.py с функцией add(a, b) и demo/test_calc.py с тестами add; все проверки контракта завершаются exit 0.

## 2. Зачем (why)

Полный цикл конвейера на изолированном модуле: контракт → исполнитель → exit-код → независимое ревью.

## 3. Файлы

**Можно менять ТОЛЬКО:**
- `demo/calc.py`
- `demo/test_calc.py`

**Можно читать (но не менять):**
- (нет)

Любой другой файл — вне контракта. Если он нужен: `NEED: <путь>` и остановись.

## 4. Интерфейсы (не выдумывать и не «улучшать»)

def add(a, b) -> int | float: возвращает a + b. Без print, без ввода, без сторонних зависимостей. demo/test_calc.py: pytest-тесты, минимум 3 кейса (положительные, отрицательные, ноль).

## 5. Критерии приёмки

1. demo/calc.py содержит функцию add(a, b), возвращающую сумму аргументов.
2. demo/test_calc.py содержит не менее трёх тестов add, включая отрицательные числа и ноль.
3. Команда pytest demo -q завершается с exit-кодом 0.
4. Команда py_compile для обоих файлов завершается с exit-кодом 0.

## 6. Вне scope (запрещено)

- Не менять файлы вне demo/calc.py и demo/test_calc.py.
- Не добавлять зависимости и не использовать сеть.

## 7. Проверки (вердикт = exit-код, текст вывода не важен)

| name | cmd | cwd |
|---|---|---|
| `compile` | `{python} -m py_compile demo/calc.py demo/test_calc.py` | `.` |
| `tests` | `{python} -m pytest demo -q -p no:cacheprovider` | `.` |
| `behavior` | `{python} -c "import sys; sys.path.insert(0, 'demo'); from calc import add; assert add(2, 3) == 5; assert add(-2, -3) == -5; assert add(0, 0) == 0; assert add(0.5, 0.25) == 0.75; print('behavior ok')"` | `.` |

`{python}` — плейсхолдер: оркестратор заменит его на текущий интерпретатор. В своих командах оставляй как есть.

## 8. Жёсткие правила для исполнителя:
- Менять можно ТОЛЬКО файлы из `files`. Нужен ещё файл — верни `NEED: <путь>`, а не догадку.
- Интерфейсы из раздела «Интерфейсы» не выдумывать и не «улучшать». Не хватает данных — `NEED: <что именно>`.
- Сеть, БД, установка пакетов — только если явно разрешено контрактом.
- Верни: список изменённых файлов; для каждой проверки — команду, exit-код и краткий фактический вывод.
  Не «всё ок», а доказательство.
- Прогоняй проверки сам ДО сдачи. Сдавать с красными проверками запрещено.
- Если требование контракта технически невыполнимо — не хакай, пиши `BLOCKED: <почему>`
  со ссылкой на строку/правило контракта.
- Не трогай `context/agent-pipeline/` — это зона оркестратора.

## 9. Типовые ловушки (реальные ошибки, стоившие раундов):
1. Контракт ссылается на канон проекта, а не на самодельные регэкспы.
2. Кэш: ключ включает ВСЁ, от чего зависит результат; ветка кэш-хита проходит ту же валидацию.
3. Счётчики не врут молча: метрику, которая должна делиться по каналам/типам, дели сразу.
4. Фолбэк «нет данных — подставь само значение» — дыра в инварианте. Формулируй, что НЕЛЬЗЯ.
5. Контракт может быть неправ, а код — прав. Сначала проверь выполнимость требования.
6. Ревьюер — отдельный вызов с лимитом контекста: заголовок и критерии → grep → range-чтения.
7. Другие процессы портят scope. Отсюда baseline и spill-исключения; `--skip-scope` — только со следом.
8. Windows/оболочки: `>` в PowerShell = UTF-16LE; `&&` может не поддерживаться; `$d:` ломает парсер.
9. JSON-контракты пиши инструментом записи целиком, а не точечными правками со вставками `\n`.
10. «Проверено» должно быть доказуемым: у факта — ссылка на источник, у отсечённого — причина.
11. Лимит раундов: 2 узких фикса на задачу. Дальше `blocked` и вопрос человеку.
